
# Oddly Wired Studio Resource Library

A curated collection of tools, platforms, asset libraries, tutorials, and technical resources discovered, researched, or evaluated for Oddly Wired Studio (OWS).

This library supports the studio as a whole, including current and future games, interactive experiences, and creative technology projects.

**Maintained by:** Oddly Wired Studio  
**Established:** November 6, 2026  
**Status:** Active

---

## Purpose

The OWS Resource Library exists to:

- Preserve useful resources discovered during research and development.
- Evaluate tools before committing studio time or money.
- Track commercial licensing, pricing, and technical compatibility.
- Identify resources that can support multiple projects.
- Document practical findings from testing and implementation.
- Reduce repeated research across studio projects.
- Build a reusable knowledge base as the studio grows.

Resources do not need to be approved, purchased, or implemented to be included.

A promising discovery is worth recording even when it does not fit the current project.

## Resource Categories

Resources are organized primarily by their function and purpose, not by the technology used to create them.

### Game Assets
**File:** [game-assets.md](game-assets.md)

- 2D art and sprites
- 3D models and materials
- Environments and tilesets
- UI and interface assets
- Asset creation tools

### Game Development
**File:** [game-development.md](game-development.md)

Game engines, frameworks, development utilities, plugins, debugging tools, procedural generation, testing tools, and deployment resources.

### Audio & Music
**File:** [audio-and-music.md](audio-and-music.md)

Sound effects, music libraries, audio creation tools, recording, editing, implementation, and licensing resources.

### Tutorials & Learning
**File:** [tutorials-and-learning.md](tutorials-and-learning.md)

Documentation, educational content, courses, technical guides, development communities, and learning materials.

Additional categories may be introduced as the studio's work expands.

## Resource Status

Each resource receives a status reflecting its evaluation or adoption.

| Status | Meaning |
|---|---|
| To Evaluate | Discovered but not yet tested |
| Testing | Currently undergoing evaluation |
| Approved | Evaluated and suitable for studio use |
| In Use | Actively supporting a studio project |
| Rejected | Evaluated and determined unsuitable |
| Archived | No longer relevant or maintained |

An approved resource is not necessarily in active use.

A rejected resource may remain documented to preserve the reasoning behind the decision.

## Standard Resource Entry

Every resource should include the following information when available.

**Resource ID:** OWS-XXX  
**Name:** Resource name  
**Website:** Official URL  
**Category:** Primary resource category  
**Subcategory:** Specific function or specialization  
**Purpose:** What the resource does  
**Potential Uses:** How OWS could apply it  
**Project Relevance:** Associated studio projects  
**Pricing:** Free, paid, subscription, or usage-based  
**Licensing:** Commercial use and redistribution considerations  
**Integration:** Relevant technical compatibility  
**Status:** Current evaluation status  
**Priority:** High, Medium, or Low  
**Date Added:** YYYY-MM-DD  
**Last Reviewed:** YYYY-MM-DD

### Evaluation Notes

Document:

- Useful capabilities and strengths
- Known limitations or risks
- Technical and visual compatibility
- Licensing questions requiring confirmation
- Testing results
- Next recommended action

Unknown information should be labeled as unverified rather than assumed.

## Public and Protected Information

This directory belongs to the public OWS website repository.

Resource documentation must not disclose:

- Proprietary systems or unreleased technical architecture
- Confidential project plans or business models
- Private access credentials or API keys
- Client or partner confidential information
- Protected project details without authorization

Public descriptions may discuss general technical relevance without revealing protected implementation details.

Detailed internal evaluations should remain in an approved private location when necessary.

---

## Maintenance Guidelines

1. Record promising discoveries, even when they are not immediately useful.
2. Check existing entries before adding duplicates.
3. Prefer official documentation and primary sources.
4. Record when pricing and licensing information was last checked.
5. Keep resource evaluations separate from marketing claims.
6. Preserve reasons for approval or rejection.
7. Update entries when resources are tested or adopted.
8. Avoid deleting historical findings merely because priorities change.
9. Keep project-specific implementation details in their appropriate project repositories.
10. Add new categories when a meaningful group of resources emerges.
